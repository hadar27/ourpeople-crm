# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Our People" — a Hebrew RTL nonprofit ERP/CRM (donors, donations, volunteers, participants, families/beneficiaries, projects, suppliers, finance, alerts, reports, users/permissions). Originally scaffolded by Lovable.

Package manager is **bun** (`bun.lock`, `bunfig.toml`), though scripts also work with npm/node.

## Commands

```sh
bun install          # install deps
bun run dev          # vite dev (TanStack Start)
bun run build        # production build
bun run build:dev    # dev-mode build
bun run preview      # preview built app
bun run lint         # eslint .
bun run format       # prettier --write .
tsc --noEmit         # typecheck (no dedicated script; used directly)
```

There is no test suite in this repo currently.

Requires Node 20.19+/22.12+ (Vite 7's minimum) — a lower Node version will make `build` fail with an unrelated-looking error. Before running any build/dev/preview command, verify the active Node is 22.x (`node -v`); if it isn't, switch with `nvm use 22` (or the closest installed 22.x version) first.

Copy `.env.example` to `.env.local` and fill in `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` (from Supabase dashboard → Settings → API Keys, the "publishable" key, not "secret") before running anything that touches data.

## Architecture

**Stack**: TanStack Start (file-based router + SSR) on Vite 7 + React 19, deployed to Cloudflare Workers via `@cloudflare/vite-plugin` (`wrangler.jsonc`, entry `src/server.ts`) and also to Vercel. Styling is Tailwind v4 + shadcn/ui ("new-york" style, see `components.json`) — RTL is handled manually via `dir="rtl"` per-component, not via a Tailwind RTL plugin. Data layer is `@supabase/supabase-js` called directly from the browser (no custom backend API, aside from one `service_role`-gated server function — see `src/lib/create-user.ts`) with `@tanstack/react-query` wrapping every call.

**Do not hand-edit `vite.config.ts` plugin list or `src/routeTree.gen.ts`** — the former is intentionally minimal because `@lovable.dev/vite-tanstack-config` already registers TanStack Start, React, Tailwind, path aliases, etc. (see the comment at the top of the file); the latter is generated by the TanStack router plugin from `src/routes/*`.

**Multi-target Nitro preset**: the shared `@lovable.dev/vite-tanstack-config` always falls back to Nitro's `cloudflare-module` preset when no explicit preset is set — it does **not** autodetect the deploy target from environment variables. `vite.config.ts` sets `nitro: { preset: "vercel" }` when `process.env.VERCEL` is set (true in Vercel's build environment) so a Vercel build gets its own `.vercel/output/**` Build Output API structure instead of a useless Cloudflare Workers script; every other build (local dev, Cloudflare) keeps the `cloudflare-module` default.

**Keep the `@tanstack/react-start`/`react-router`/`router-plugin`/`react-query` family in lockstep**: these are tightly coupled pre-1.0 packages, and `bun.lock` had them pinned to a bad combo (`@tanstack/react-start@1.167.50` + `@tanstack/router-plugin@1.167.28`, with `@tanstack/react-router` at `1.168.25`) where `createServerFn(...).validator(...)` genuinely threw `TypeError: X(...).validator is not a function` in production client bundles — confirmed by rebuilding from that exact locked combo and inspecting the minified output: the compiled `createServerFn` object was missing its `validator` key (only `inputValidator` survived whatever dead-code-elimination pass ran), while `create-user.ts`/`delete-user.ts`/`update-user-email.ts` all call `.validator(...)`. Bumping the whole family together (`bun update @tanstack/react-start @tanstack/router-plugin @tanstack/react-router @tanstack/react-query`) fixed it — a partial bump (react-start/router-plugin only, leaving react-router behind) breaks the build instead with `"getScriptPreloadAttrs" is not exported by "@tanstack/router-core"`, so always update the four together and rebuild before committing a bump. If a `.validator is not a function` (or similar) error ever comes back, verify with `VERCEL=1 vite build` locally and grep the built `.vercel/output/static/assets/module-edit-dialogs-*.js` for `.validator(` — a clean build has zero matches, and the property (`validator` vs only `inputValidator`) is visible directly in the minified `createServerFn` object literal if you need to confirm which build produced a given artifact.

**Registry hygiene when running any `bun install`/`bun update` locally**: this repo's dependencies must resolve from the public npm registry (plus the `@lovable.dev/*`/`nitro`/`oxc-parser` packages' private Lovable mirror, which `bun.lock` already pins to explicit tarball URLs) — never from a personal/company registry override in `~/.npmrc` or a global bunfig. A polluted lockfile shows up as `bun.lock` diffs where generic packages (e.g. `@babel/*`) gain an explicit registry URL where they previously had `""` (empty = default registry). If you see that, `git checkout -- bun.lock` and rerun with `BUN_CONFIG_REGISTRY=https://registry.npmjs.org` forced.

### Routing

File-based routes in `src/routes/`, TanStack Router convention: `_app.<name>.tsx` are authenticated pages nested under the `_app` pathless layout route (`_app.tsx` → `AppShell`); `_app.<name>_.$id.tsx` are detail pages (the trailing `_` before the param makes the URL segment plain, e.g. `/donor/$id` not nested under `/donor`). `__root.tsx` sets up `<html dir="rtl" lang="he">`, global `<head>` tags, the React Query provider, toaster, and error/not-found boundaries. `login.tsx` and `index.tsx` are unauthenticated.

`AppShell` (`src/components/app-shell.tsx`) is the sidebar/topbar layout and also the auth gate: it redirects to `/login` when `useSession()` has no session. Session state comes from `src/lib/auth.ts` (`useSession`, `signOut`), which wraps Supabase Auth and resolves client-side only (avoids SSR/localStorage hydration mismatch).

### Data layer

- `src/lib/supabase.ts` — the one browser-usable Supabase client instance, read from `VITE_SUPABASE_*` env vars (publishable key only).
- `src/lib/queries/*.ts` — one file per entity, real Supabase CRUD via react-query hooks (`use<Entity>()`, `use<Entity>s()`, `useCreate<Entity>()`, `useUpdate<Entity>()`). **`queries/suppliers.ts` is the reference pattern** most other query files mirror: a `*Record` (camelCase, app-facing) type and a `*Row` (snake_case, DB-facing) type, `toXRecord`/`toRow` mappers, a `xKeys` query-key factory, and query-invalidation in mutation `onSuccess`. Follow this shape for any new entity or field.
- `src/lib/create-user.ts` — the app's one server-only code path: a TanStack Start `createServerFn` that runs in the Cloudflare Worker, never the browser. It uses a `service_role` Supabase admin client (built from `SUPABASE_SERVICE_ROLE_KEY`, read via `process.env` — never `VITE_`-prefixed, never bundled client-side) to call `auth.admin.createUser` and insert the matching `public.users` row, gated on the caller's own session being an active `"מנהל מערכת"` (checked server-side via `canEditModule`, not trusted from the client). Copy `.dev.vars.example` to `.dev.vars` (gitignored) for local dev; set the same key in production with `wrangler secret put SUPABASE_SERVICE_ROLE_KEY`.
  - **Don't put `createServerFn` definitions under a directory literally named `server/`** — `vite.config.ts`'s `@lovable.dev/vite-tanstack-config` adds an import-protection rule (`client.files: ["**/server/**"]`) that unconditionally blocks client code from importing anything under such a path, even a legitimate `createServerFn` export meant to be called from the client. Keep server-function modules at a normal path (e.g. directly in `src/lib/`); the build fails with an `[import-protection]` error otherwise.
- `supabase/migrations/*.sql` — numbered, additive migration files (no migration CLI wired up in this repo, so these are applied by hand against the Supabase project). `0001_full_migration.sql` is the original full DB schema (RLS policies `to authenticated`, explicit `GRANT`s per table); later files (`0002_...`, `0003_...`) are incremental changes layered on top — don't rewrite `0001` retroactively, follow the pattern of wrapping in `begin;`/`commit;` with `if exists`/`if not exists` guards so a migration is safe to re-run.
- `src/lib/mock-data.ts` / `src/lib/crm-seed.ts` — static/seed data still used by some entities and by the dashboard, reports page, and the `business-rules.ts` alert engine. Not every entity reads from Supabase; check the relevant `queries/*.ts` (or lack thereof) before assuming a given module is live-data-backed.
- `src/lib/business-rules.ts` — the alert engine (`generateAlerts()`). Pure business rules, no AI, deliberately (per original spec in `README.md`).
- `src/lib/permissions.ts` — role→module edit matrix (`canEditModule`, `useCanEdit`). The signed-in user (`useCurrentUser()`) is the real Supabase Auth session's user, matched by email against the `public.users` directory table — not mocked.
- `src/lib/edit-forms.ts` — shared form field defs (`*Fields`) and validation patterns (`ID_PATTERN` = 9-digit Israeli ID, `PHONE_PATTERN` = 10-digit phone) used by the generic edit dialogs.

### Shared UI

`src/components/ui/` is shadcn/ui generated components (don't hand-roll equivalents). `src/components/data-table.tsx`, `detail-kit.tsx`, `page-header.tsx`, `form-dialog.tsx`, `entity-form-dialog.tsx`, `record-edit-dialog.tsx`, `module-edit-dialogs.tsx` are the hand-built generic building blocks most list/detail pages compose (dynamic tables, search/filter chrome, add/edit dialogs driven by the `edit-forms.ts` field defs). Prefer composing these over writing bespoke per-page table/dialog markup.

### SSR error handling

`src/server.ts` wraps the TanStack Start server entry: it catches thrown errors *and* detects the case where the underlying `h3` server swallows an in-handler throw into a generic 500 JSON body (`isCatastrophicSsrErrorBody`), and in both cases renders a branded error page (`src/lib/error-page.ts`) instead of a raw error. `src/lib/error-capture.ts` is what stashes the original error so it can still be logged. Don't remove this wrapping when touching server entry/build config — it's there because h3's default behavior on SSR crashes is an unhelpful blank JSON response.

### Conventions

- Path alias `@/*` → `src/*` (see `tsconfig.json`, `components.json`).
- Prettier: 100-char width, double quotes, semicolons, trailing commas everywhere — run `bun run format` rather than hand-wrapping.
- User-facing strings, including enum-like status values (e.g. `"פעיל"`, `"מושעה"`), are Hebrew and used as literal TypeScript union types — match existing values exactly rather than inventing new status strings.
- `src/lib/version.ts` (`APP_VERSION`) is bumped manually and logged to the console on app load (`__root.tsx`). **Do not bump this yourself** — only change it when the user explicitly asks.
